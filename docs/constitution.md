# constitution.md — Конституция проекта

---

## 1. О проекте
- **Название / гипотеза:** Mood Diary — см. `hypothesis.md`
- **Что строим одной фразой:** Android-приложение — ежедневный дневник настроения для реального клиента, который выявляет паттерны (в первую очередь связь сна и настроения) и даёт мягкие персональные рекомендации.
- **Что осознанно НЕ строим:** Интеграции с внешними трекерами сна/активности/питания/календаря, мобильное приложение (веб-версию), полноценный ML-анализ, работу со специалистами внутри продукта, push-уведомления — всё это осознанно вне скопа MVP.

## 2. Технологический стек
> Что агенту разрешено использовать. Всё, чего здесь нет, — под запретом без согласования.
- **Язык(и):** Python (бэкенд); Kotlin (Android-приложение) — **рабочее допущение, требует подтверждения от Никиты до начала W3**, финально фиксируется в `plan.md`.
- **Фреймворк / платформа:** бэкенд-фреймворк уточняется на этапе Plan (W3); на фронтенде — нативная Android-разработка (Jetpack Compose как рабочее предположение, финально фиксируется в `plan.md`).
- **Хранилище данных:** PostgreSQL. MVP поддерживает реальные данные реального клиента (не только моки) — команда осознанно выносит юридические аспекты (согласия, комплаенс, регуляторные требования к данным о здоровье) за рамки проекта.
- **Запрещено:** платные внешние API, сложные интеграции, тяжёлые зависимости, смена языка бэкенда или БД без согласования с командой.

## 3. Правила кода и архитектуры
> Как агент должен писать код.
- **Стиль / соглашения:** PEP8 для Python-кода, понятные имена переменных/функций, без избыточной абстракции ради абстракции.
- **Структура проекта:** чёткое разделение бэкенда (API на Python) и Android-приложения (Kotlin); структура каталогов фиксируется в `plan.md` на W3.
- **Простота:** предпочитать минимальное рабочее решение (MVP-скоп из `hypothesis.md`/`spec.md`), не усложнять раньше времени. Алгоритм рекомендаций на старте — простое правило на основе научно подтверждённой корреляции сон–настроение (см. `research.md`), а не ML-модель.
- **Каждая задача проверяема** по критериям приёмки из `spec.md`.

## 4. Ограничения безопасности и приватности
- MVP работает с реальными данными реального клиента; юридические аспекты (согласия, комплаенс) вне скопа проекта по решению команды.
- Не хранить секреты и ключи в коде (переменные окружения / .env, исключённый из репозитория).
- Доп. правила:
  - Базовая инженерная гигиена сохраняется даже без юридического фокуса: доступ к БД ограничен, данные не логируются в открытом виде, нет передачи данных третьим лицам и аналитическим SDK.

## 5. Границы автономности агента
> Что агент делает сам, а где обязан остановиться и спросить команду.
- **Может сам:** писать и рефакторить код бэкенда/фронтенда в рамках уже согласованного стека и MVP-скопа, добавлять тесты, писать документацию, предлагать мелкие технические решения внутри выбранного стека.
- **Должен спросить перед:** сменой стека (язык, БД, фреймворк), удалением данных, выходом за скоп MVP (например, добавлением интеграций или push-уведомлений без согласования), любым решением, затрагивающим приватность данных.

## 6. Definition of Done
> Когда работа считается завершённой.
- Соответствует спецификации `spec.md` и критериям приёмки.
- Прототип запускается и демонстрирует главный сценарий из `hypothesis.md` (быстрая отметка состояния → визуализация динамики → инсайт по паттерну → рекомендация).
- Доп. условия:
  - Лог одной записи занимает ≤15–20 секунд (ключевое требование из `research.md`).
  - Первый содержательный инсайт показывается пользователю уже при небольшом объёме данных (3–5 записей), а не требует недель использования.

## 7. Процесс и ограничения проекта
- **Время:** прототип за 4 воркшопа (≤ 2 ч каждый) + межсессионные задания.
- **Формат результата:** мобильное приложение (Android).
- **Источники правды:** `hypothesis.md` → `research.md` → `spec.md` → `plan.md` → `tasks.md`.
