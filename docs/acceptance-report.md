# Отчёт о проверке критериев приёмки — Mood Diary (P0)

**Дата проверки:** 27.07.2026
**Проверяемая сборка:** debug (`app-debug.apk`), `versionName = 1.0`, `applicationId = com.mooddiary`
**Реализация:** [MainActivity.kt](../app/src/main/java/com/mooddiary/MainActivity.kt) (единый файл, Kotlin + Jetpack Compose)
**Хранилище:** локально на устройстве через `SharedPreferences` + JSON (`LocalMoodStore`)
**Источник критериев:** [spec.md](spec.md) §5, §7 (US-0…US-STAT), §11 (Definition of Done)

## Окружение и метод

- Эмулятор `mood_pixel6_api35` (Pixel 6, google_apis x86_64, API 35), Android 15.
- Проверка комбинированная: (1) прогон реального приложения в эмуляторе со снятием скриншотов; (2) инспекция кода `calculateInsight`/`LocalMoodStore` для веток, которые тяжело воспроизвести вручную.
- Состояния инсайтов воспроизводились сидированием `SharedPreferences` тестовыми записями (метод — в конце отчёта). После проверки данные приложения сброшены (`pm clear`) — приложение возвращено к первому запуску.
- Скриншоты-доказательства: [docs/acceptance-report-assets/](acceptance-report-assets/).

**Обозначения:** ✅ выполнено · ⚠️ выполнено с замечанием / требует уточнения · ❌ не выполнено · ⏭️ P1 (вне scope P0).
Тип доказательства: *(экран)* — проверено в эмуляторе, *(код)* — проверено инспекцией кода.

## Замечания (не блокирующие)

1. **US-4 — формулировка прогресса.** Реализованы визуальный счётчик «{x}/3» и «{x}/5» + прогресс-бар, но текст подзаголовка отличается от дословного в спеке («Нужно ещё 1 запись…» вместо «{x}/3 записей до первой проверки…»). Смысл сохранён, §5.4 разрешает адаптацию текста. *Рекомендация:* при желании выровнять с эталонной формулировкой.

2. **US-2 / §5.2 — `stable_low`/`stable_high` при 3–4 записях.** Код выдаёт статус `found` для стабильных веток уже при 3–4 записях (напр., 3 записи все `sleep ≤ 2` → `found / stable_low`). §5.2 требует при 3–4 показывать мини-инсайт «только при явной связи», а примеры §5.3 для стабильных веток приведены на 5 записях. *Рекомендация:* подтвердить, что стабильные ветки — это «явная связь» для 3–4, либо ограничить их порогом 5+.

3. **US-6 — оценка только для `found`.** Строка «Полезно/Не полезно/Пропустить» показывается только при статусе `found`. Критерий US-6 сформулирован для «показанного инсайта» без ограничения статусом. Поведение разумно (оценивается реальное наблюдение), но формально шире критерия. *Рекомендация:* подтвердить желаемое поведение.

4. **§6.3 / DoD-12 — нет UI ошибки сохранения.** Явного сообщения об ошибке сохранения нет. Риск низкий: запись идёт в локальный `SharedPreferences`, введённые значения остаются в состоянии экрана до навигации. *Рекомендация:* при переходе на постоянное хранилище (Room) добавить обработку ошибки.

5. **Стек хранения.** Реализовано на `SharedPreferences` + JSON, а не на Room/SQLite. Требование «локальное хранение на устройстве» (constitution) и privacy-first — выполнены. Но это отклонение от плана «Room», зафиксированного в заметках проекта. *Рекомендация:* подтвердить выбор хранилища на этапе Plan/Implement.

## Как воспроизвести проверку состояний инсайтов

Состояния сидировались напрямую в `SharedPreferences` (debug-сборка, эмулятор с `adb root`):

1. `adb root`
2. Записать XML вида `<map><boolean name="disclaimer_shown" value="true"/><string name="entries">[…JSON записей…]</string></map>` в `/data/data/com.mooddiary/shared_prefs/mood_diary.xml`, выставить владельца `u0_a209` и `restorecon`.
3. `adb shell am force-stop com.mooddiary` перед записью, затем `am start -n com.mooddiary/.MainActivity`.

Наборы для ключевых состояний:
- **`not_enough_data` + прогресс:** 2 записи.
- **`found / contrast` + вторичное (энергия):** сон `2 5 2 4 5`, настроение `2 4 3 4 5`, энергия `2 4 2 4 5`.
- **`waiting`:** 3–4 записи без контраста и без стабильной ветки.
- **`no_clear_pattern`:** 5+ записей без корреляции (напр., сон `3 3 3 3 3`).

Сброс к чистому состоянию: `adb shell pm clear com.mooddiary`.
